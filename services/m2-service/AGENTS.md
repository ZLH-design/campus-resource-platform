## 2. 调用 M1 的接口（契约已冻结）

```
POST /api/m1/seat-restrictions
Authorization: Bearer <jwt>
X-Idempotency-Key: M2:<申请单UUID>:<APPLY|RELEASE>
Content-Type: application/json

{
  "sourceType": "M2",
  "sourceId":   "<申请单主键，UUID>",
  "ownerUserId": "<申请人用户 ID，UUID，必传>",
  "roomId":     "<教室主键，UUID>",
  "startAt":    "2026-10-22T01:00:00Z",
  "endAt":      "2026-10-22T05:00:00Z",
  "action":     "APPLY"
}
```

**什么时候调：**

| M2 动作 | 调用 |
|---|---|
| 审批通过 | `action: "APPLY"` |
| 驳回 / 申请人撤销 / 超时撤销 | `action: "RELEASE"` |

**四个容易错的：**

1. **不传 `seatId`** —— 整间教室占用，M1 内部展开全部座位
2. **`sourceId` 必须是 UUID** —— 申请单主键不要用自增 int，契约里有正则，"1001" 会被直接拒绝
3. **时间 UTC 带 `Z`**
4. **APPLY 必须带 `ownerUserId`（申请人用户 ID）** —— 漏传直接 400。
   这是给 M1 存的：将来报修撞上你的借用、M1 清退时，靠它知道该通知谁。
   不带这个字段，M1 只知道申请单号，找不到人。

**幂等是安全的**：APPLY 两次只有一条记录（第二次 `created: false`）；RELEASE 两次第二次什么都不做。
所以你重试、事务回滚重发时**不需要自己做去重**。

**错误返回对照：**

- 400 参数错（字段名拼错、类型错、时间格式错、多传字段、M2 缺 `ownerUserId`）
- 401 token 无效
- 403 服务账号无权操作该教室
- 409 **该教室该时段已有其他生效限制**（另一张申请单已通过，或教室正在维修）——见下方「审批互斥」

遇到 400，先对照 yaml 的 `SeatRestrictionCommand` 查字段名和类型，**不要猜**。

## 3. 状态机（本轮要交付）

状态列表：草稿 / 待初审 / 待终审 / 已通过 / 已驳回 / 已撤销 / 已超时

每条转换写成：`当前状态 --[触发事件 + 操作人]--> 下一状态`
并标注哪条要调 M1、用 APPLY 还是 RELEASE。

**两级审批规则**：所属院系/空间管理员（`APPROVER_DEPT`）初审 → 校级资源管理员（`APPROVER_UNIVERSITY`）终审。
审批总时限 **3 天**（读参数 `BOOKING_APPROVAL_TIMEOUT_DAYS`，从 `d-config-parameter.yaml`），
超时未处理则申请自动撤销（M2-005，定时任务，身份规则见 `common.yaml` 的 `x-system-identity`）。

角色名从 `openapi/common.yaml` 的 `Role` 枚举取，**不要自己写 "admin" 之类**。

标注两个非法转换的例子及应返回的错误码。

**审批互斥（重要，两层防护缺一不可）：**

| 层 | 在哪 | 做什么 |
|---|---|---|
| 第一层 | **你的审批接口内** | 审批人点「通过」前，查自己库里同教室、时段重叠（半开区间）、已 APPROVED 的申请 —— **同一时段只能通过一张**。第二张的审批人应看到「该时段已被占用」，只能驳回 |
| 第二层 | M1 的 409 | 两个审批人**同一秒**都点通过时，第一层同时放行两张 → 第二张 APPLY 撞 M1 的 409 兜底 |

第二层命中 409 时的处理：申请单转「已驳回」，原因标注「教室该时段不可用」，
通知申请人（`BOOKING_REJECTED`）——**不要让申请单停留在已通过状态**，那是最坏结果。

**注意**：第一层只能看见你自己库里的申请单，**看不见 M3 的维修**。
所以「批了一间正在维修的教室」只能靠第二层 409 拦，这不丢人，是设计好的分工。

**超时撤销 vs 人工审批的竞态（已定决策，三条都要做）：**

| 规则 | 内容 |
|---|---|
| **截止静默期** | 距超时截止（提交后 3 天，读 `BOOKING_APPROVAL_TIMEOUT_DAYS`）**不足 10 秒时，审批接口拒绝受理**，返回 409「该申请即将超时自动撤销」。让定时任务赢赢得干干净净，不跟人抢最后几秒 |
| **后到者失败** | 状态转换加乐观锁（版本号）。静默期把窗口压到极小但不是零 —— 两个写操作仍然可能同时到达，此时**后提交的失败**，不是两个都成功 |
| **APPLY 在途补偿** | 审批先成功、APPLY 已发出，定时任务这时才撤销（按 SI-5 查状态本应跳过，但要防边界）：M2 检测到申请单已不是 APPROVED 时，**必须补发一条 RELEASE** 把座位占用吐出来。不许留下「单子已撤销、教室还占着」的脏状态 |

**审批通过的执行顺序与补偿（已定决策：顺序 B）：**

审批人点「通过」后，系统要做三件事：改状态（自己的库）→ 调 M1 APPLY（跨网络）→ 写审计（跨网络，`APPROVAL_DECIDE`）。三步不在同一事务里，**按顺序 B 执行，两个失败分支各配一条补偿**：

| 步骤 | 失败在哪 | 补偿动作 |
|---|---|---|
| 1. 改状态（乐观锁）→ 2. APPLY → 3. 写审计 | 第 2 步 APPLY 失败（网络/409） | 状态回滚至审批前，通知审批人「占用失败，请重试或驳回」 |
| | 第 3 步审计失败（契约规定审批类审计失败必须回滚，见 d-audit.yaml） | 状态回滚 + **补发 RELEASE** 把教室吐出来 |

选 B 不选 A（先审计后 APPLY）的理由：A 断掉时「批了没占到」，社团到现场才发现，最伤；
B 断掉时「占了没批成」，补偿链能自动纠正，学生侧只是座位短暂不可约。
补偿 RELEASE 与上表「APPLY 在途补偿」是**同一段代码**——检测申请单状态与座位占用不一致即发 RELEASE，一次实现两处复用。

**驳回后不可重投**：同一教室同一时段被驳回后，不允许重新提交申请（common.yaml 的 AW-2）。
重投会把审批窗口推到学生预约开放日，重新打开冲突窗口。
